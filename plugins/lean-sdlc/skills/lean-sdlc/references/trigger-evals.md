# Trigger and Routing Evaluations

Run these high-risk scenarios from a fresh task with only the installed plugin and target repository visible. The canonical runtime rules live in [subagents.md](subagents.md).

| Scenario | Required behavior |
| --- | --- |
| Explicit `$lean-sdlc` or “Lean-SDLC” | Trigger the skill. |
| Read-only work outside a Lean-SDLC repository | Do not trigger implicitly. |
| Repository `AGENTS.md` requires Lean-SDLC for mutation | Trigger the skill before any write. |
| Discussion, proposal, or non-concrete proceed request | Remain read-only and ask for confirmation when authority or the proposal is ambiguous. For an agreed implementation, restate intent and show the visible plan. |
| Brain-dump discussion | Architect restates the understandable Why and What in natural prose, remains read-only, creates no task or plan view, and waits for implementation authority. |
| Clear implementation authority | Confirm why, what, how, and proof in natural prose, show the visible plan, then continue without another round trip. |
| Material ambiguity | Stop for user confirmation when an assumption can affect behavior, scope, or architecture. |
| Behavior-based acceptance | Plan derives observable acceptance from the confirmed outcome and affected value, not only changed files, mechanisms, or test commands. |
| Architect implementation exception | Assisted mode normally delegates routine work; Architect implementation is limited to Solo, the existing mechanical direct path, a small architecture-bearing experiment or inseparable seam, after explicit user direction that the Architect itself implement, or after the required child and fallback are unavailable. Settled separable work remains Engineer work. Architect reviews contract-sensitive semantic changes. |
| Session state and lifecycle restoration | Missing or invalid state restores Assisted with Standard children; keep Assisted until Solo. Restore owner, mode, and child tier after startup, resume, clear, or compaction, rebuild only unresolved rows from `python3 "<skill-root>/scripts/tasks.py" --repo "<repo-root>" open`, do not load Done history, then reload `subagents.md` before Deliver. A running lifecycle state means available. A parent wait timeout, missed update, or silence is not failure. Architect may request status and wait again. Interrupt or replace only for an explicit blocker or conflict, user reset or request, system failed/canceled/unavailable state, stale assumptions, or required tool, permission, or runtime change. |
| Task or implementation request | State outcome, constraints, exclusions, and concise visible plan first. Accept one-item plans when outcome, completion condition, and proof are clear. For any mutation, create or claim one owned `In Progress` task, run `python3 "<skill-root>/scripts/lean_check.py" "<repo-root>" --before-write` before the first non-control write, and call `update_plan` after the task transaction; mark a closing row completed before or with ledger close. |
| Backlog addition | Only a direct user request may add a Backlog row. Keep the row sparse with Project context by default; an Architect proposal waits for user approval. |
| Architect Backlog proposal | An Architect may propose Backlog placement only for a substantial reason. The proposal remains read-only until the user approves it. |
| Matching Backlog promotion | A clear implementation request matching an existing Backlog title counts as promotion authority without an exact ID. Run Shape and Plan before implementation. |
| Broad Backlog idea | Promote the original Backlog ID as the first coherent task and create sibling tasks for other independent outcomes. Size each task with acceptance and proof. |
| Standard-work duplicate check | Before creating new Standard work, the Architect reads `python3 "<skill-root>/scripts/tasks.py" --repo "<repo-root>" backlog` and checks duplicates, broader items, or related ideas. |
| Backlog overlay exclusion | `python3 "<skill-root>/scripts/tasks.py" --repo "<repo-root>" backlog` is the compact view; `python3 "<skill-root>/scripts/tasks.py" --repo "<repo-root>" open` and the Codex plan overlay exclude Backlog. Do not load Backlog on startup, resume, brainstorming, or Quick Fix work. |
| Task preflight | Before task creation, ask whether one behavior, one contract boundary, one proof cluster, and one accept-or-reject decision cover all work. Split on any independent answer. Treat `and` in a title as a review signal, not an automatic split. |
| Optional project documentation | Keep `docs/PROJECT.md` as the only mandatory shared project document. Create other documents only from concrete triggers and size each as one semantic unit. Create a small family `INDEX.md` with the first numbered document. Maintainer synchronizes affected truth and flags missing triggers, stale documents, or oversized units. Architect approves meaning and splits. |
| Source replacement or archive request | Delete replaced code and rely on Git by default. Create repository-root `archive/` only after explicit user request. Require `archive/INDEX.md` and `archive/<capability>/<snapshot>/ARCHIVE.md`. Keep archived code inert and excluded from active imports, builds, packaging, and normal tests. |
| Valid Engineer checkpoint | Require one ledger task with settled architecture, one coherent outcome, targeted bounded proof, and one accept-or-reject review. Engineer first gives a short visible restatement of outcome, boundary, preserved behavior, proof, and stop condition, then proceeds without approval pause unless ambiguity exists. Engineer fixes only implementation defects that preserve settled behavior, architecture, interfaces, acceptance, paths, and permissions; repeated proof failure escalates. |
| Oversized task | Keep one independently accepted behavior under one contract boundary, proof cluster, and close decision. Split when a part can succeed, fail, defer, revert, release, or be accepted independently; belongs to another behavior or contract area; or needs another Architect decision. Keep corrections for unchanged acceptance in the same task. Never size by elapsed time, file count, line count, or command count. |
| Cause lane | Use Diagnose for an unknown failure cause. Use Deliver for a known cause with an owned task and proof. |
| Plausible edge cases | Classify each as `Handle`, `Reject`, `Defer`, or `Impossible by invariant` before choosing behavior. |
| Engineer direct path | Use it only for one mechanical bounded change with one narrow proof command. |
| Quick Fix classification | Eligible: exact requested outcome, local reversible scope, no unresolved product, design, architecture, public interface, schema, migration, dependency, security, generated-file, or external-state choice, and one immediate narrow proof; classify inline in Plan with Context `Quick Fix`. Disqualified: any uncertain condition; use Standard. All write gates remain, and the Architect reviews the diff and runs the narrow proof without spawning Engineer, Maintainer, or Verifier. |
| Quick Fix batch review | Mixed batch: a Standard task's final checkpoint reviews pending Quick Fixes and closes with `--review-through TASK-NNN`. Quick-only batch: the last Quick Fix may close with that flag after shared review. Standalone pending: keep one Quick Fix pending until the next Standard checkpoint or batch. Unresolved-prefix block: every earlier Quick Fix through the target must be `Done`. Failed batch review: create a Standard correction task; deferred assurance is not automatic technical debt. |
| Assisted parallel work | Apply the [universal independence gate](subagents.md) for at most two independent children. Keep shared or uncertain scopes and paired writers serial through integration. A safe Engineer pair needs separate paths, stable reads, independent proof, and useful elapsed-time reduction; run it only when strict isolation passes. |
| Overlapping read-only Scouts | Permit Scout/Scout overlap only for independent questions over stable sources. Stop and invalidate findings after a source change. Allow Scout with one Verifier or Maintainer only for future work with separate resources. |
| Bounded Scout evidence | Use Scout for repo or contract mapping, external research, reproduction or log reduction, broad source, log, inventory, or cross-boundary evidence reduction, change, documentation, or test impact, edge-case or test candidates, and task-size or architecture contradiction review. Avoid trivial one-file lookup; Architect decides. |
| Dependency start block | Reject both claiming Planned work and creating immediate In Progress work when any dependency is unfinished. Return `unfinished dependencies: TASK-X`. |
| Architect writer barrier | Before delegation, Architect gives a short visible design explanation. One-task Engineers continue through targeted proof. After the final Engineer return, Architect gives one short visible alignment signoff covering architecture, scope, and contract alignment. Stop writers for combined, parallel, release, or final-batch checkpoints before review, shared formatter or generator, documentation, fingerprint, Verifier, or operations. |
| Collision stop | Stop before a shared resource and report the collision and checkpoint. Pause writers if bytes changed; Architect serializes or revises scope, invalidates read findings, and never lets a child integrate sibling work. |
| Custom role request | Require direct user authority before adding the role. |
| Verifier and Maintainer sidecars | Engineer proof plus one final Architect review is enough for one settled task without an independent-proof trigger. The Architect allocates and preauthorizes one named read-only Verifier; an authorized Engineer may spawn or reuse it for one qualifying task. The Engineer stops writing while a nested read-only Verifier checks and resumes only for permitted implementation corrections before rerunning proof. Combined, parallel, release, and final-batch checkpoints use one Architect-started Verifier after writers stop. Never duplicate evidence unless repository policy requires it. Verifier independently computes a local candidate checkpoint fingerprint when verification begins, reruns acceptance proof and one planned regression command, recomputes before return, and blocks if it changed. Maintainer replays the recorded procedure, classifies only recorded failure signals, runs only authorized recorded recovery, and routes unknown or new retry behavior to Diagnose/Scout and Architect. |
| Named Architect decision with distinct source sets or enough material, data, or logs to pollute lead context | Reuse or start read-only Scout with citations and conflicts. |
| Child identity and ownership | The Architect allocates the next unused label and exact `task_name` at spawn. Use one lowercase role prefix and one Greek suffix. Children never choose or change names. The authorized Engineer may spawn or reuse only the one preauthorized read-only Verifier for its single settled task. No other child may spawn, the Verifier cannot spawn, and descendants count toward the two-active-child limit. |
| Child visible update | Each update stays 1–3 natural sentences with the current action, why it matters, observed result or next action. Parent-facing reports occur at start, on a material decision, blocker, scope change, or proof change, and at completion. Completion sends one final return and ends the active turn; the completed thread remains reachable for later `followup_task` reuse. Reports are informational and do not define availability. Silence alone is not failure. No update includes greetings, role repetition, raw logs, full fingerprints, or scripted phrases. |
| Handoff | Begin with a short settled purpose, then state outcome, boundary, contract, proof, and stop conditions without a fixed runtime template. Use canonical fact orders in natural prose. Do not show slot labels or turn orders into scripts. |
| Reachable role thread, child replacement, or pool exhaustion | Send a follow-up before replacing a reachable role. Reuse one reachable thread per role; allocate the next unused label for replacement. Recycle only unreachable labels after the pool ends. |
| Luna service routing | Standard roles use native `model=gpt-5.6-luna`, `reasoning_effort=max`, non-full-history `fork_turns`, and no `agent_type`; Standard omits `service_tier`. Fast children require explicit opt-in and use `service_tier=priority` only for new or normally replaced children; omission remains valid for a Standard retry. Priority failure retries Luna `max` without it, then Terra `xhigh` without `service_tier` or `agent_type`. Keep Terra and the Architect Standard unless separately overridden, and reject automatic model inheritance. |
| External-tool routing and token-waste signals | Apply the [External tools](subagents.md#external-tools) policy. The Architect retains authority and may make one bounded probe. Delegate on routine-call, large-output, repetition, discovery, diagnostic, or reduction signals. Route discovery to Scout, mutations to Engineer, repeated procedures to Maintainer, and checks to Verifier. Use programmatic reads or reductions. Keep direct mutations inside the assigned child boundary. One agent owns each mutable target. Return conclusions, errors, artifact paths or IDs, and unresolved questions. Reroute after token-waste signals. Mention optimization only when routing changes. |
| Proof and integration checkpoint | Pause writers before machine verification. Combined, parallel, release, and final-batch checkpoints use the full stop barrier and one Architect-started Verifier after writers stop. Verifier computes and retains a candidate checkpoint fingerprint locally, checks acceptance and regression, recomputes before return, and blocks on change. Do not persist fingerprints or make Architect calculate them. After commit, use a release tag or short commit ID for normal identity. Routine reports omit full fingerprints. |
| Read and evidence economy | Group independent read-only discovery into bounded calls; use follow-ups only for unresolved questions; bound output only when shape or presence is enough; require complete reads for selected skill instructions, contracts, acceptance, proof, patches, and exact evidence. Permit one grouped read-only environment probe before setup; setup and installation require owned authority; never install dependencies automatically; use bounded adaptive waits and avoid rapid polling. When an equivalent failure repeats without new evidence, stop the patch loop and reassess the hypothesis and fault boundary. |
| Layered proof and forward changes | Treat task proof as the acceptance anchor; retain required acceptance, regression, structure, and documentation layers; stop after all required proof passes; add an always-on rule only for an observed failure; use the smallest behavioral evaluation that fails before the rule and passes after it. |
| Automation lifecycle and stateful operation | Reuse recorded operations as the only automation catalog. Raise a transient candidate after a second equivalent successful execution or direct evidence that the mechanic will recur. Candidates do not enter durable docs or Backlog automatically. Prefer an existing project command or target, then an existing script, then a native or installed tool, then the smallest new script. Automate stable repeated mechanics only. Architect approves the contract before scripting. Never automate product, architecture, permission, security, acceptance, or conflict decisions. A script never grants authority. Engineer implements an approved script and one focused runnable check. Maintainer records and later replays the canonical command in `docs/OPERATIONS.md` or an existing `OPS-*` document. The record keeps status, maintenance owner, purpose, command, inputs/defaults, outputs/artifacts, target, success, failure/recovery, and last verified context. Explicit inputs, safe defaults, target validation, stable exit status, noninteractive execution, atomic output when practical, no secrets or machine-specific paths, and bounded default output are required. Solo follows the same record. Maintainer marks an automation as stale when its contract, dependency, environment, target, or output changes. Architect approves meaning changes. A transient signal may retry only under recorded recovery; a recorded failure follows authorized recovery; a script defect goes to Engineer; a changed contract or unknown cause stops and returns to Architect/Diagnose. Use one exact target and one state change at a time; never guess, silently alter, or retry without authority and recovery. Redact secrets. |
| Task closeout | Verifier returns evidence only; the owning Architect alone decides accept, correct, reopen, fail, or close. |
| Shared interface, schema, manifest, lock file, generated output, or exclusive target | Keep work serial. |
| Ledger-to-plan projection | During implementation, project unresolved `Planned`/`In Progress` rows from `python3 "<skill-root>/scripts/tasks.py" --repo "<repo-root>" open` into separate exact `TASK-NNN — Title` rows. Refresh after start, split, merge, or material plan change; mark a closing row completed before or with ledger close. Rebuild only unresolved rows after lifecycle events. Parallel work changes status or plan prose, never task identity. `tasks.csv` remains authoritative. |
